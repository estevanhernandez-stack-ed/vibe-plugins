# Vibe-Eval v0.2 candidate: app-callable eval endpoint

**Captured:** 2026-05-28 during v0.1 round-trip operational friction
**Status:** Design candidate, not in v0.1

## The idea

Apps optionally expose a dev-only endpoint that vibe-eval calls instead of calling the vendor SDK directly. The endpoint wraps the app's existing model client, so vibe-eval gets EXACT production-fidelity testing for free — no composer-mimic approximation, no separate credentials.

## The contract

App exposes (for example) `POST /api/dev/vibe-eval-proxy`:

**Request body:**

```json
{
  "promptId": "natal_interpretation",
  "fixture": {"name": "Maya Okafor", "chartData": "..."},
  "model": "gemini-2.0-flash"
}
```

**Response body:**

```json
{
  "output": "<the actual model response>",
  "tokens": {"input": 8240, "output": 612},
  "costUsd": 0.0024,
  "model": "gemini-2.0-flash",
  "composedPromptPreview": "<first 500 chars of what was actually sent>"
}
```

vibe-eval's `AppEndpointClient` makes the HTTP call. App-side handler:

1. Resolves `promptId` against the app's own prompt registry
2. Fills the prompt with `fixture` vars (the app's templating, not vibe-eval's)
3. Applies the app's actual composer (the real `gemini.ts` stack, not a mimic)
4. Calls the vendor SDK with the app's real credentials
5. Returns the response + cost accounting

## Why this is better than v0.1's direct-vendor approach

| Concern | v0.1 direct call | v0.2 app endpoint |
|---|---|---|
| Production fidelity | Approximates via composer-mimic | Exact — uses the real composer code path |
| Credential management | vibe-eval needs its own vendor key | App handles its own auth — vibe-eval needs none |
| Composer drift | Risk: captured composer goes stale when app changes | None — the app's current code runs |
| Multi-vendor support in vibe-eval | One client per vendor | One `AppEndpointClient` covers any vendor the app supports |
| Setup friction for users | Configure vendor keys + composer interview | App author adds ~30 lines once |
| Cost accounting accuracy | Estimated from token counts + vibe-eval's rate table | Exact — app reports actual cost from vendor response |

The app-endpoint pattern is structurally cleaner across every dimension that matters. The v0.1 direct-call path stays useful only as a fallback for apps that haven't adopted the endpoint pattern yet.

## Open design questions

1. **Endpoint discovery.** How does vibe-eval find the endpoint? Options:
   - Convention: `/api/dev/vibe-eval-proxy` at the app's base URL
   - Config: `.vibe-eval/config.json` field `appEndpoint: "https://localhost:3000/api/dev/vibe-eval-proxy"`
   - Manifest: app declares the endpoint in its `package.json` or a `vibe-eval.json` file

2. **Auth between vibe-eval and the app.**
   - Bearer token? Shared secret? IP allowlist (localhost-only)?
   - Most apps will want the endpoint to be unreachable in production builds
   - Suggestion: env-gated (`if (process.env.NODE_ENV !== 'development') return 404`) + optional shared-secret header

3. **Schema validation.** The app endpoint should validate its responses against a published schema (`app-endpoint-response.schema.json`) so vibe-eval can trust the shape.

4. **App-side adapter library.** Should vibe-eval ship a tiny TS/JS lib (or Python equivalent) that apps can import to implement the endpoint with minimal boilerplate?
   - `@vibe-eval/app-adapter` package with helper: `createEvalEndpoint(modelClient, registry)`
   - User: `export default createEvalEndpoint(technomancerModel, DEFAULT_PROMPTS)`

5. **Streaming.** v0.1 sends one request, gets one response. Vertex AI / Gemini both support streaming. v0.2 endpoint contract might want streaming for long generations.

6. **Cost reporting.** How does the app know the exact cost? Most vendor SDKs return token counts but not dollar cost. App-side adapter would need a rate table OR the app declares "I don't know cost; vibe-eval should estimate."

7. **Backward compatibility with v0.1's direct-call path.** v0.2's `run` SKILL should detect (a) is there an app endpoint config? → use AppEndpointClient. (b) Otherwise → fall back to direct vendor call with composer-mimic. Both paths coexist.

## Migration story for v0.1 → v0.2

For Celestia3 (and any app that adopts the endpoint pattern):

1. Add `pages/api/dev/vibe-eval-proxy.ts` (~30 lines using a `@vibe-eval/app-adapter` helper if one exists, or hand-rolled if not)
2. Update `.vibe-eval/config.json` to add `appEndpoint: "http://localhost:3000/api/dev/vibe-eval-proxy"`
3. Delete `.vibe-eval/composer.json` (no longer needed when app endpoint is in use)
4. Run `/vibe-eval:run` — same UX, but now testing through the real composer/proxy path

For apps that don't adopt: nothing changes. vibe-eval continues using the direct-vendor + composer-mimic path from v0.1.

## Why this might be a major version (v1.0 or even a separate plugin)

Honest read: the app-endpoint pattern is substantial enough that it could justify being its own plugin (`vibe-eval-app` or similar) OR a major version. Reasons:

- Different security model (app holds credentials, not vibe-eval)
- Different schema (endpoint config, response schema)
- Different vendor abstraction (one `AppEndpointClient` replaces N vendor clients)
- Different cost model (app reports actual cost)
- Different setup flow (no `gcloud auth login`, no API key in env)

A separate plugin might let vibe-eval ship the cleaner architecture without the complexity tax of supporting both paths. But it also fragments the marketplace, and most users will benefit from having both options in one tool. Lean toward "v2.0 of the same plugin" rather than spawn.

## Validation app

When this lands, the same Celestia3 cowpath story applies: add the dev-only endpoint to Celestia3 first, dogfood, capture process-notes, then generalize the SKILL.

## Trigger for promoting this design pass

Either:
- v0.1 ships and dogfooding surfaces "composer-mimic is too brittle" friction in evolve-eval logs
- A second/third target app needs vibe-eval and the composer-mimic interview takes >1 hour to get right
- User signal: "wouldn't it be cleaner if the app just exposed an endpoint?"

The last one already fired (this doc). Promote design pass when v0.1 stabilizes.
